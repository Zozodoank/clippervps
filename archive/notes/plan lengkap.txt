# Rencana: ClipperVPS di VPS Ubuntu 22.04 — Oracle Qwen2.5-VL-3B Lokal + yt-dlp via Jaringan HP

## Ringkasan Keputusan Arsitektur (sudah diverifikasi terhadap kode)

1. **Kontrak oracle TIDAK diubah sama sekali.** Notebook Kaggle hanyalah *klien* dari `server/api/routes/vlmOracleRoutes.js` (`claim` → unduh frame → `result`). Penggantinya adalah **worker Python lokal di VPS** yang memanggil `http://127.0.0.1:5000/api/vlm-oracle/claim` dengan `protocolVersion = '2026-10-06-grid-v1'` (konstanta `ORACLE_GRID_PROTOCOL` di `server/services/vlmOracleService.js` L23). Heartbeat (`touchOracleHeartbeat` di jobStore.js L631) otomatis terpelihara dari claim — gerbang strict di `stage1Render.js` L355–399 (`assertOracleConnected`) **tetap lulus tanpa perubahan 1 baris pun**.
2. **Runtime model:** `llama.cpp` `llama-server` (API kompatibel OpenAI) + `Qwen2.5-VL-3B-Instruct` GGUF Q4_K_M + mmproj. Alasan: CPU VPS tidak butuh CUDA/torch/pip; RAM ±2,5 GB; satu biner, satu file konfigurasi.
3. **Routing yt-dlp via HP:** HP (Termux) menjalankan SOCKS5 server (`microsocks` port 1080) dan SSH **reverse tunnel** `-R 10808:127.0.0.1:1080` ke VPS. `downloader.js` `getSmartProxyArgs()` (L90–106) SUDAH membaca `RESIDENTIAL_PROXY`/`PROXY_URL` dan memeriksa `/proc/net/tcp` sebelum memakai `--proxy` — di Ubuntu 22.04 mekanisme ini bekerja apa adanya; bila tunnel mati, yt-dlp diam-diam lanjut direct (tidak merusak job).
4. **`VISION_VERIFY_MODE=oracle` tetap**, `ORACLE_AUTO_LAUNCH=0` (tidak ada kaggle CLI di VPS). Jalur Kaggle **tidak dihapus** — tetap tersedia sebagai fallback manual.

## Fase A — Persiapan VPS Ubuntu 22.04 (infrastruktur)

**Target:** SSH `ubuntu@208.76.40.194 -p 14115` (password ada di `server/.env` `VPS_PASSWORD`; executor wajib memakai password dari `.env`, bukan menyalinnya ke output/log).

1. **`A1. Buat skrip `setup-vps.sh`** di root repo (pola `setup-termux.sh`: idempoten, `set -e`, log per langkah). Isi:
   - `sudo apt-get update && sudo apt-get install -y git curl wget ffmpeg python3 python3-venv python3-pip build-essential cmake pkg-config ca-certificates`
   - Node.js 20 LTS via NodeSource (wajib ≥20: `better-sqlite3@13` di `server/package.json`), lalu `npm i -g pm2`.
   - yt-dlp: unduh biner release terbaru ke `/usr/local/bin/yt-dlp` (`chmod +x`) — jangan pip (pip kadang lebih tua).
   - Clone repo ke `/opt/clippervps`; `npm install` di `server/` dan `client/`.
   - **whisper.cpp** (path `.env` sudah menunjuk `/root/clippervps/server/bin/whisper/whisper-cli` — sesuaikan agar cocok dengan layout `/opt/clippervps` ATAU simpan repo di `/root/clippervps` agar path `.env` lama tetap valid; rekomendasi: **clone ke `/root/clippervps`** supaya tidak perlu mengubah `WHISPER_CPP_BIN`/`WHISPER_MODEL`): clone `ggerganov/whisper.cpp`, `make`, unduh `ggml-base.bin` → `server/bin/whisper/models/`.
   - **llama.cpp**: clone `ggerganov/llama.cpp`, `cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build --config Release -j$(nproc)` → biner di `build/bin/llama-server`.
2. **`A2. Unduh model** ke `/opt/clippervps-models/` (pakai `wget -c` agar resume):
   - GGUF utama: repo `bartowski/Qwen2.5-VL-3B-Instruct-GGUF` file `Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf` (fallback bila nama file berbeda di HF: `ggml-org/Qwen2.5-VL-3B-Instruct-GGUF` atau `mradermacher/…`; verifikasi dengan `llama-server --version` + uji smoke Fase B).
   - mmproj: `mmproj-Qwen2.5-VL-3B-Instruct-f16.gguf` dari repo resmi `ggml-org`.
3. **`A3. Verifikasi dasar:** `ffmpeg -version`, `yt-dlp --version`, `node -v` (≥20), `python3 --version`, `whisper-cli -h` jalan, `llama-server --version` jalan. Simpan bukti di log setup.

**Gerbang A:** semua biner tervalidasi; repo ter-clone; `npm test` di `server/` hijau (vitest, DB terisolasi — jangan sentuh `jobs.db`).

## Fase B — Oracle Lokal Qwen2.5-VL-3B (pengganti Kaggle)

1. **`B1. Buat `server/oracle_local/worker.py`** — port TEPAT dari `kaggle/vlm_oracle_qwen.py` (jangan tulis ulang dari nol), ganti `ask()` transformers → HTTP ke llama-server. Kontrak fungsi yang wajib dipertahankan identik:
   - `main()` loop: `POST {BASE_URL}/api/vlm-oracle/claim` body `{"workerId":"local-vps","protocolVersion":"2026-10-06-grid-v1","sourceHash":md5(__file__)}` header `x-api-token`; `claimed:false` → baca `pending`/`activeJobs`, sleep `ORACLE_POLL_SEC` (default 2 s; worker sistemd/PM2 selalu hidup, TIDAK ada idle-exit).
   - `verdict_batch()`: unduh frame `GET {BASE_URL}{url}` (header token) → `prep_image` (MAX_SIDE=1024) → `ask()` batch → **recovery chain sama persis**: `prompt_retry` (compact prompt) → `split2` (chunk 2 frame) → `single_frame`; grid mode: `resolve_grid_cell_verdicts` + `infer_grid_cell` (crop sel dari grid `raw%03d.jpg`, `col=cell%2, row=cell//2`).
   - `ask()` baru: `POST {LLAMA_SERVER_URL}/chat/completions` dengan `messages=[{role:"user", content:[{type:"image_url", image_url:{url:"data:image/jpeg;base64,…"}}…, {type:"text",text:prompt}]}]`, `temperature:0`, `max_tokens:ORACLE_MAX_NEW_TOKENS` (128). Pertahankan `looks_degenerate` + `extract_json` (bracket-balancing sadar-string) + `median_int` + `clamp_score` **byte-per-byte** dari notebook.
   - `post_result()`: `POST {BASE_URL}/api/vlm-oracle/result` body `{batchId, attempt, workerId, protocolVersion, verdict|error}`; tangani 409 (expired/worker_mismatch) & 404 (pruned) & 426 (protocol mismatch) persis notebook.
   - Env worker: `ORACLE_BASE_URL=http://127.0.0.1:5000`, `ORACLE_TOKEN` (dibaca dari `server/.env` `API_ACCESS_TOKEN`), `LLAMA_SERVER_URL=http://127.0.0.1:8080/v1`, `ORACLE_NO_MODEL=1` untuk dry-run (klaim+unduh+report TANPA model — sama dengan pola dry-run Kaggle).
2. **`B2. Jalankan llama-server** via PM2 (bukan nohup):
   `llama-server -m /opt/clippervps-models/Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf --mmproj /opt/clippervps-models/mmproj-…-f16.gguf --host 127.0.0.1 --port 8080 --ctx-size 4096 --threads $(nproc) --parallel 1`
3. **`B3. Smoke test dua lapis:**
   - `curl http://127.0.0.1:8080/health` → `{"status":"ok"}`.
   - Satu gambar uji 9:16 via `/v1/chat/completions` → JSON `{"safe":…}` ter-parse. **Bila format image gagal** (llama.cpp perlu format `image_url` data-URL), sesuaikan `ask()`; ini satu-satunya titik integrasi yang boleh berubah.
   - Dry-run worker (`ORACLE_NO_MODEL=1`) + enqueue batch tiruan (pakai harness gaya `scratch/termux_repro_fg.sh`): pastikan claim→download→result tercatat di `server/logs/audit.log` dan `GET /api/vlm-oracle/status` menunjukkan `connected:true`, `workerId=local-vps`, `protocolVersion=2026-10-06-grid-v1`.
4. **`B4. Daftarkan PM2**: `pm2 start worker.py --name oracle-local --interpreter python3`, lalu `llama-server` → nama `oracle-model`, `dev-runner.js` → `clipper`; `pm2 save`.

**Gerbang B:** status oracle `connected:true` dengan worker `local-vps`; grid batch ter-claim (cek field `cells` di log claim); dry-run beres tanpa error.

## Fase C — Belokkan jaringan yt-dlp VPS ke HP (SOCKS5 reverse tunnel)

1. **`C1. Sisi HP (Termux)** — buat `scripts/phone-proxy-connect.sh` + panduan di `ORACLE_VPS.md`:
   - `pkg install openssh microsocks` (autossh opsional).
   - `ssh-keygen` + `ssh-copy-id -p 14115 ubuntu@208.76.40.194` (sekali).
   - Jalankan `microsocks -i 127.0.0.1 -p 1080` di sesi Termux (atau Termux:Boot).
   - Jalankan tunnel persisten: `autossh -M 0 -N -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes -R 10808:127.0.0.1:1080 -p 14115 ubuntu@208.76.40.194` (tanpa autossh: loop `ssh -N …` dengan retry). Skrip di HP boleh `.sh` sederhana; Termux:Boot script disertakan di panduan.
2. **`C2. Sisi VPS**: `server/.env` tambah `PROXY_URL=socks5h://127.0.0.1:10808` (baris komentar lama di `.env` L35–38 sudah mendokumentasikan desain ini). **Tidak ada perubahan kode `downloader.js`.**
3. **`C3. Verifikasi routing:**
   - `curl --socks5-hostname 127.0.0.1:10808 https://api.ipify.org` → harus mengembalikan IP publik HP (bukan IP VPS).
   - `yt-dlp --proxy socks5h://127.0.0.1:10808 --skip-download -O "%(title)s" <URL YouTube uji>` sukses.
   - Matikan tunnel di HP → jalankan satu job tiruan download → pastikan `getSmartProxyArgs()` melewatkan `--proxy` (log `[Downloader] 🛡️` tidak muncul) dan job tidak crash.
4. **`C4. (Opsional, dianjurkan) flag `YTDLP_PROXY_REQUIRED`**: di `downloader.js` `getSmartProxyArgs()`, bila proxy localhost diset TAPI tidak listening DAN `YTDLP_PROXY_REQUIRED==='1'` → throw error jelas "Proxy HP tidak tersambung" (fail-fast) alih-alih unduh direct dari IP datacenter (risiko blokir YouTube). Default `'0'` = perilaku lama. Tambah 3–5 unit test untuk `getSmartProxyArgs` (mock `fs.existsSync` + env) di `server/tests/downloaderProxy.test.js`; tambahkan ke `FLAG_NORMALIZERS` di `server/config/runtimeFlags.js` (nilai `=== '1'`) agar beku per-job.

**Gerbang C:** IP lewat proxy = IP HP; download YouTube lewat HP sukses; fallback direct tetap berfungsi saat tunnel mati.

## Fase D — Penyesuaian Alur Kerja VPS (env + E2E job nyata)

1. **`D1. `server/.env` (VPS, hasil akhir) — ubah hanya baris berikut** (sisanya biarkan):
   ```
   PROXY_URL=socks5h://127.0.0.1:10808
   ORACLE_AUTO_LAUNCH=0                      # tidak ada kaggle CLI di VPS
   VLM_ORACLE_BASE_URL=http://127.0.0.1:5000 # worker lokal, bukan tunnel
   VLM_ORACLE_TOTAL_TIMEOUT_SEC=3600         # CPU 500 frame ± 125 pass grid
   VLM_ORACLE_TIMEOUT_SEC=300                # per batch (sudah aman)
   VLM_ORACLE_CONNECT_TIMEOUT_SEC=60         # worker lokal klaim < 5 dtk
   APP_TIMEZONE=Asia/Jakarta                 # quota harian benar di VPS (UTC)
   ```
   Pertahankan: `VISION_VERIFY_MODE=oracle`, `VLM_ORACLE_GRID=2`, `VLM_ORACLE_MAX_FRAMES=500`, `VLM_ORACLE_AUDIT_MAX_FRAMES=240`, `VLM_ORACLE_FRAME_HEIGHT=240`, `RENDER_DOWNLOAD_SECTIONS=1`, `RENDER_NO_FULL_DOWNLOAD=1`, `API_ACCESS_TOKEN` (wajib — endpoint oracle menolak 503 tanpanya), `CLOUDFLARE_TUNNEL_URL`/`PUBLIC_BASE_URL` (untuk akses UI via ngrok; **matikan ngrok di HP/Termux dulu** — ngrok free hanya 1 sesi per domain).
2. **`D2. Cosmetic (rendah risiko):** ubah teks pesan gerbang `assertOracleConnected` (vlmOracleService.js L111–140) dari "Oracle Kaggle" → "Oracle lokal Qwen (VPS)" agar log/riwayat job tidak menyesatkan. Jangan sentuh logika. Update string terkait di `stage1Discovery.js` L484. Jalankan `npm test` (test `vlmOracle.test.js` tidak mengunci teks — verifikasi dulu sebelum ubah; bila ada assertion teks, sesuaikan snapshot secara eksplisit).
3. **`D3. Benchmark oracle lokal** — buat `scratch/bench_oracle_vps.sh`: enqueue N batch grid (8/16/32/64 frame) → catat `elapsedMs` per batch dari vonis (field sudah ada di `normalizeOracleVerdict`) → tabel tuning. Target awal: < 30 s per grid pass. Kalau > 60 s: turunkan `VLM_ORACLE_MAX_FRAMES` ke 240 dan/atau `VLM_ORACLE_FRAME_HEIGHT` tetap 240.
4. **`D4. Job manual E2E nyata** (gerbang P1 yang selama ini terbuka — lihat `RANGKUMAN_CLIPPER.md` §13.6): 1 kandidat YouTube kitchen lewat UI (via tunnel) atau curl `POST /api/generate` dengan token. Cek urutan: download via proxy HP → `frames_raw` → oracle claim/result (`server/logs/job-trace.jsonl` + `audit.log`) → `cleanFrames≥3` → render → FINAL QC → `completed`. Bandingkan `GET /api/job-trace/<jobId>`: event lengkap, `provider=yt-dlp` dengan proxy aktif.
5. **`D5. Auto mode E2E**: 1 produk via `/api/auto/start` → discovery → render → `completed`. Ledger `product_rejects.json` tidak mencatat kegagalan infra (perilaku sudah ada).

**Gerbang D:** 1 job manual + 1 job auto `completed` dengan vonis lokal; trace job menunjukkan stage oracle lulus; tidak ada pesan "Kaggle" tersisa di log job baru.

## Risiko & Mitigasi

| Risiko | Mitigasi |
|---|---|
| Format image llama-server tidak kompatibel dengan klien port-an | Smoke test B3 sebelum apa pun; sesuaikan `ask()` saja (format `data:image/jpeg;base64`); pin versi llama.cpp yang terbukti di `ORACLE_VPS.md` |
| CPU lambat → total timeout 1800 s jebol | Benchmark D3; naikkan `VLM_ORACLE_TOTAL_TIMEOUT_SEC=3600` (sudah default baru); turunkan `VLM_ORACLE_MAX_FRAMES` bila perlu |
| Tunnel HP putus di tengah job | `getSmartProxyArgs` sudah melewatkan proxy (job lanjut direct); `YTDLP_PROXY_REQUIRED` (C4) untuk fail-fast bila operator maunya tegas; autossh/`ServerAliveInterval` menjaga tunnel hidup |
| IP datacenter VPS diblokir YouTube saat proxy mati | Proxy = jalur utama (socks5h); cookies.txt tetap didukung (`findCookiesFile`); fallback `COBALT_API_URL` sudah ada di `downloader.js` |
| Worker lokal mati → job menumpuk | Fail-closed bawaan: tanpa claim → gerbang menolak job baru `reason:never_claimed`; PM2 auto-restart worker + llama-server |
| ngrok domain bentrok dengan sesi HP | Matikan tunnel ngrok di HP/Termux sebelum start di VPS (ngrok free 1 sesi); `start-tunnel.sh auto` di VPS via PM2 |
| Path whisper `/root/clippervps/…` salah di VPS | Clone repo ke `/root/clippervps` (bukan `/opt`) agar path `.env` lama valid; atau bangun whisper.cpp ke path yang sama |
| Job lama di-retry dengan snapshot mode lama | `configSnapshot` membekukan `VISION_VERIFY_MODE=oracle` + flag oracle — retry memakai nilai beku (sudah ada, `configSnapshot.test.js`) |

## Alternatif yang Ditolak

- **Menulis ulang kontrak oracle menjadi panggilan in-process Node ke llama-server** → menyentuh `vlmOracleService`/`stage1Render`/`jobStore` yang sudah teruji 157+ tes; kehilangan jejak audit claim/result; risk besar tanpa benefit.
- **`ORACLE_OFFLINE_CALIBRATION=1` untuk "melihat output tanpa oracle"** → melanggar mandate strict oracle-only (ditolak eksplisit di `plan lengkap.txt` fase 1); tidak dipakai.
- **transformers/torch CPU di VPS** → deps berat, fp16 6 GB RAM, jauh lebih lambat dari GGUF Q4 via llama.cpp.
- **vLLM** → butuh GPU; VPS target adalah CPU.
- **vite dev server untuk produksi** → dipertahankan sementara (terbukti di Termux via PM2); opsi lanjutan: `vite build` + serve `client/dist` dari Express (catat di `ORACLE_VPS.md` sebagai TODO, jangan dikerjakan sekarang).
- **Proxy komersial sebagai ganti jaringan HP** → berbayar; user eksplisit minta jaringan HP.
